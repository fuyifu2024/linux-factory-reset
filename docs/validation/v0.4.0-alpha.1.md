# v0.4 acceptance / 验收记录

## Local IMG recovery: passed / 本地 IMG 恢复通过

[Real UEFI VM run 42382115771](https://github.com/fuyifu2024/linux-factory-reset/actions/runs/42382115771), application commit `d519c6c2edc368ecb5917c9071cee7293a31d86d`.

The disposable AMD64 VM used an official Debian 13 NoCloud image. Its target filesystem UUID and GPT partition GUIDs were changed before boot, ensuring relocation could not succeed merely because source and target identities happened to match. A separate ext4 recovery disk held the pristine IMG and package. Test setup created an old user, personal files under `/home` and `/root`, and an extra application file.

The VM ran the real `prepare-image` and `arm --reboot` commands. The generated initramfs verified media, restored the root and FAT boot filesystems, relocated boot pointers, cleared the request and rebooted into the first-user service. QMP keyboard input drove the actual first-user script. An observer verified the new account, sudo membership and locked root credential. The host then mounted the powered-off disk read-only and independently checked the synced PASS result, expected new account, absence of the old account/files and cleared reset request.

[Persistent guest result](v0.4.0-alpha.1/local-img-result.txt). The observer adds logging/checks around the production first-user script but retains its body and terminal input. It does not replace account creation with a mock. Serial output alone is insufficient because a serial getty can reset its terminal during shutdown; the persistent result and offline checks are mandatory.

## Limits / 边界

This evidence covers a Debian 13 AMD64 UEFI VM with ext4 root and FAT ESP. It does not establish physical-hardware recovery, ARM64 guest boot, generic Ubuntu reboot recovery, Secure Boot, power-loss recovery or secure disk erasure. ISO automatic installation, the Fedora restore engine and Mint integration are unimplemented. Download capability is not a claim of a working restore engine for every distribution.

All compilation, image mounting and VM restore ran on disposable remote runners. The user's Pi was not compiled on, reset, rebooted or subjected to large-image workloads.
